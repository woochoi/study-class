# ISMS-P 스터디 까페 — 1차 구현(5~7단계) 설계

- 작성일: 2026-11-03
- 상위 문서: [CLAUDE.md](../../../CLAUDE.md) (프로젝트 PRD 역할)
- 참고 자료: [CPPG 법령 허브.html](../../../CPPG%20법령%20허브.html), [CPPG 시행령 허브.html](../../../CPPG%20시행령%20허브.html)

표기: **(결정)** = 사용자가 정한 것, **(설계자 판단)** = 대화 중 제안했고 사용자가 이의를 제기하지 않은 것 또는 작성자가 정한 것. 빌더가 바꿔도 되는 부분은 「빌더 재량」에 따로 모았다.

## 1. 의도 — 왜 만드는가

ISMS-P / CPPG를 준비하는 사람들이 **함께** 개인정보 보호법을 공부하는 온라인 공부방이다.

공부하다 가장 자주 막히는 순간은 이것이다 **(결정)**:

> 대시보드에서 법 조문을 따라 내려가다 시행령에 이르면 "세부 기준은 보호위원회가 고시한다"로 끝난다. 실제로 무엇을 해야 하는지(예: 「개인정보의 안전성 확보조치 기준」 제7조 암호화 대상·방식)는 고시 원문을 봐야 알 수 있는데, 지금 허브 HTML에는 "고시 제7조"라는 번호만 있다.

그래서 이번 구현의 중심은 **법 → 시행령 → 고시를 한 화면에서 원문으로 보는 것**, 그리고 거기서 막히면 **바로 질문을 올리고 다른 스터디원이 답하는 것**이다.

## 2. 목표 · 비목표 · 실패 조건

### 2.1 목표 (이번 5~7단계)

| # | 목표 | 성공 기준 |
|---|---|---|
| M1 | 구글 로그인 | 구글 계정으로 로그인 → 새로고침·서버 재시작 후에도 로그인 유지, 로그아웃 가능 |
| M2 | 법령 대시보드 | 기존 「CPPG 법령 허브」의 5개 탭이 DB 데이터로 동작, 진도가 사용자별로 DB에 저장 |
| M3 | 3단 원문 조회 | 조문 번호를 누르면 법 · 시행령 · 고시 원문이 세 칸으로 나란히 표시 (예: 법 제29조 → 영 제30조 → 고시 제4~12조) |
| M4 | 문의 게시판 | 로그인 사용자 누구나 질문·답변, 답변 달린 질문은 목록에 표시, 3단 화면에서 조문이 붙은 질문 작성 |
| M5 | CLAUDE.md G2~G4 유지 | 데이터 영속성, 서버 전용 DB 접근 + 파라미터화 SQL, Supabase/Neon에서 같은 `init.sql`로 재생성 |

### 2.2 비목표 (이번에는 하지 않음, 나중에 할 수 있음)

- **복습 리마인드 퀴즈** — 3단 화면을 "계단식(법 → 영 각 호 → 고시)"으로 한 단계씩 펼치는 B안 시안은 이 퀴즈용으로 나중에 쓴다 **(결정)**. 시행령 허브의 간격 반복(1→3→7→14→30일)도 이때 함께.
- **시험 문제 풀이 · 오답노트** **(결정: 나중으로)**
- **개인정보보호위원회 결정문 API** **(결정: 나중으로)**. 응답에 관련 조문 번호가 있는지 확인되지 않았다. 3단 화면 아래에 "관련 결정문" 칸이 들어갈 자리만 레이아웃상 남겨 둔다.
- 게시판: 알림(이메일·푸시), 답변 채택, 추천, 첨부파일, 대댓글 **(설계자 판단)**
- 「안전성 확보조치 기준」 외의 고시 **(결정)**
- Supabase/Neon 실제 이전, Render 등 배포 (CLAUDE.md 1.4)
- 상태관리 라이브러리, ORM, 인증 라이브러리(Auth.js 등)

### 2.3 실패 조건 (기술적으로 동작해도 실패로 보는 것)

- 조문 원문이 틀리거나 오래된 것인데 그 사실이 화면에 드러나지 않음 → 모든 원문에 **기준 법령(공포번호·시행일)과 받아 온 날짜**를 표시한다.
- 외부 API가 느리거나 막혔을 때 3단 화면이 안 뜸 → 원문은 **미리 받아 DB에 저장**하고 화면은 DB에서만 읽는다.
- 브라우저 번들에 DB 접속 정보·구글 client secret·법령 API `OC` 값이 들어감.
- 다른 사람 글을 수정·삭제할 수 있음.

## 3. 제약

CLAUDE.md 4~6장을 그대로 따른다. 요약:

- Next.js 16.4 App Router + TypeScript, 데이터 변경은 **Server Actions**, 읽기는 서버 컴포넌트.
- PostgreSQL 17 (Docker Compose, named volume). Next.js는 macOS에서 `npm run dev`.
- `pg` 직접 사용, 모든 SQL은 `$1, $2` 파라미터화, DB 모듈은 `import 'server-only'`.
- 표준 PostgreSQL SQL만 (확장 없음). 같은 `db/init.sql`로 Supabase/Neon 재생성 가능.
- 런타임 의존성 최소화 (`next`, `react`, `react-dom`, `pg`).
- 비밀값은 `.env`(Git 제외), 이름만 `.env.example`에 커밋.

### 3.1 CLAUDE.md 규칙의 예외 (결정)

- **구글 OAuth 콜백 Route Handler 하나만 허용한다.** 예: `app/auth/google/callback/route.ts`. 구글이 로그인 후 사용자를 돌려보내는 주소를 받으려면 필요하다. 그 외 `app/api/*`·REST 엔드포인트는 여전히 만들지 않는다.
- 이 결정을 CLAUDE.md 1.4 비목표 항목 옆에 한 줄로 명시한다.

### 3.2 REST API를 만들지 않는 이유 (결정, 기록용)

나중에 Supabase나 Neon으로 옮겨도 둘 다 표준 PostgreSQL이므로 `DATABASE_URL`만 바꾸면 된다. REST API는 이전에 도움이 되지 않는다. REST API가 필요해지는 경우(모바일 앱 같은 외부 클라이언트, `supabase-js`로 브라우저에서 직접 DB 호출)는 현재 계획에 없다.

이전할 때 확인할 점을 `docs/DB_DESIGN.md`에 남긴다: SSL(`sslmode=require`), 커넥션 풀러 주소(Supabase Supavisor / Neon `-pooler`), Supabase에서는 테이블 RLS 활성화(서버 전용 접속이라 정책은 비워도 됨).

### 3.3 추가 환경 변수 (설계자 판단)

| 변수 | 용도 |
|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | 구글 OAuth 클라이언트 (사용자가 Google Cloud Console에서 직접 발급) |
| `APP_URL` | 콜백 주소 조립용, 개발 시 `http://localhost:3000` |
| `LAW_API_OC` | 국가법령정보센터 OPEN API 인증값 (사용자가 직접 활용신청, 승인 1~2일) |

## 4. 사용자와 흐름

**사용자**: 로그인해서 함께 공부하는 모든 사람. 관리자·답변 전담자는 따로 없다 **(결정)**.

**대표 흐름** (CLAUDE.md 2장 + 이번 대화):

1. 구글로 로그인한다.
2. 대시보드(개요·진도 탭)에서 배점 대비 덜 본 단원을 확인한다.
3. 조문 매핑표나 앵커에서 **법 제29조**를 누른다.
4. 3단 원문 화면에서 법 제29조 · 영 제30조 ①항 각 호 · 고시 제4~12조를 나란히 읽는다.
5. 모르는 부분이 있으면 화면 아래 **"이 조문에 대해 질문하기"**를 누른다 → 조문 태그가 붙은 질문 작성.
6. 다른 스터디원이 질문 상세 화면 아래에 답을 단다 → 목록에 "답변 있음" 표시.
7. 회독 체크·암기 카드 단계를 누르면 내 계정에 저장된다.

## 5. 기능 상세

### 5.1 구글 로그인 (5단계)

- 구글 OAuth 2.0 Authorization Code 흐름을 **직접 구현**한다 (결정). `fetch` + Node 내장 `crypto`만 사용.
  - 로그인 시작: Server Action이 `state`(CSRF 방지 난수)를 만들어 `httpOnly` 쿠키에 넣고 구글 인증 주소로 redirect.
  - 콜백 Route Handler: `state` 검증 → code를 토큰으로 교환 → ID 토큰에서 `sub`, `email`, `name`, `picture` 확보 → 사용자 upsert → 세션 생성 → 쿠키 설정 → 원래 보던 페이지로 redirect.
- 처음 로그인하면 자동 가입 **(설계자 판단)**. 표시 이름은 구글 이름.
- 사용자 식별은 `(provider, provider_user_id)` 조합으로 한다. 나중에 Supabase Auth 등으로 바꿔도 사용자 데이터가 유지되게 하기 위함 **(설계자 판단)**.
- 세션: DB `sessions` 테이블에 저장, 브라우저에는 무작위 세션 토큰만 담은 `httpOnly; Secure(운영); SameSite=Lax` 쿠키. DB에는 토큰의 해시를 저장 **(설계자 판단)**.
- 로그아웃: Server Action으로 세션 행 삭제 + 쿠키 제거.
- 비로그인 사용자도 대시보드·3단 원문·게시판 **읽기**는 가능. 진도 저장·질문·답변은 로그인 필요 **(설계자 판단)**. 비로그인 상태에서 진도 버튼을 누르면 로그인 안내.

### 5.2 법령 대시보드 (6단계)

**뼈대는 「CPPG 법령 허브」의 5개 탭** (설계자 판단): 개요·진도 / 마인드맵 / 암기 카드 / 조문 매핑표 / 개정 연혁.

- **시행령 허브에서 합칠 것**: 세부 항목별 "법 ↔ 시행령" 짝 데이터(`DOMAINS[].units[].items`)와 시행령 장별 조문 색인(`DECREE`)을 조문 매핑표 탭에 합친다.
- **어느 조문 번호를 눌러도** 3단 원문 화면(5.3)이 열린다.
- **진도 방식**: 법령 허브의 단순 방식 — 중단원별 1·2·3회독, 암기 카드 3단계, 시험일(D-day). 시행령 허브의 간격 반복은 비목표.
- **진도 저장**: 사용자별로 DB에 저장 (브라우저 localStorage 대신). 다른 기기에서 로그인해도 이어짐.
- **암기 카드 범위** (설계자 판단): 법령 허브 `CARDS`에 더해 시행령 허브의 세부 항목 카드(`ITEMS`, `DEC_CARDS` — `DOMAINS`·`DECREE`에서 만들어짐)도 포함한다. 카드 탭의 "범위" 선택에 "법률 카드 / 시행령 카드"를 추가한다. 진도는 모두 법령 허브의 3단계 방식.
- **참조 데이터**: 두 HTML 안의 JS 배열(`AREAS`, `CHAPTERS`, `ANCHORS`, `MNEMO`, `CARDS`, `HISTORY`, `DOMAINS`, `DECREE`, `TIMELINE`)을 DB 참조 테이블로 옮기고 seed SQL로 넣는다. 화면은 DB에서 읽는다.
- 화면 디자인(색상 토큰, 대단원 고유색 5개, 폰트)은 법령 허브 HTML의 스타일을 따른다.
- 기준 법령 표기: 법률 제21445호(2026. 9. 11. 시행), 시행 예정 제21910호(2027. 3. 9. 시행, 제28조의12~15), 시행령 대통령령 제36671호. 허브의 `🔜 시행예정` 표시 방식 유지.

### 5.3 3단 원문 조회 (6단계)

**화면: A안 — 세 칸 나란히** (결정, 시안: `.superpowers/brainstorm/…/three-tier-layout.html`)

```
┌ 법 제29조 안전조치의무 ──────────────────────────────────────┐
│ [법률]            │ [시행령]              │ [고시·안전성 확보조치 기준] │
│ 제29조 원문        │ 제30조 ①항 1~n호 원문 │ 제4조 내부 관리계획 …       │
│                   │ ③ 세부는 고시로 …     │ 제7조 암호화 …             │
├──────────────────────────────────────────────────────────────┤
│ 기준: 법률 제21445호 · 받아 온 날짜 2026-11-xx                │
│ [이 조문에 대해 질문하기]   이 조문의 질문 3개 ▸              │
│ (관련 결정문 — 자리만, 이번엔 비움)                           │
└──────────────────────────────────────────────────────────────┘
```

- 넓은 화면은 가로 3칸, 좁은 화면(휴대폰)은 세로로 쌓는다 **(설계자 판단)**.
- 칸 안 원문은 조·항·호·목 구조를 살려 보여준다.
- 화면 아래: "이 조문에 대해 질문하기" 버튼 + 이 조문 태그가 붙은 질문 목록 링크.
- 시행령이나 고시가 없는 조문은 해당 칸에 "시행령 조문 없음" 등 안내 (허브의 `ⓘ` 표기 방식).

**원문 출처와 저장** (결정: 법령 API 이번에 사용 / 설계자 판단: 저장 방식)

- 법률·시행령 원문: **국가법령정보센터 OPEN API**.
- 고시 원문: 같은 API의 **행정규칙 본문 조회**를 먼저 시도한다. 조문 단위로 받을 수 없거나 내용이 부족하면 **`docs/sources/`의 PDF**로 채운다 (아래 「로컬 원문 자료」).
- **법 조문 ↔ 시행령 조문 ↔ 고시 조문 연결**: 3단 비교 API 또는 위임법령 조회가 조문 단위 연결을 주면 그것을 쓰고, 고시 연결이 빠져 있으면 허브 HTML의 매핑(예: `영30① · 고시 제7조`)을 seed로 넣어 보완한다.
- **원문은 미리 받아 DB에 저장**하고 화면은 DB만 읽는다. 받기는 서버에서만 실행되는 동기화 스크립트(예: `npm run sync:laws`)로 사람이 직접 돌린다. 런타임에 화면 요청마다 외부 API를 부르지 않는다.
- 저장할 때 기준 법령(공포번호·시행일)과 받은 시각을 함께 저장해 화면에 표시한다.
- 법제처 출처 표기를 화면 하단에 넣는다 (API 이용 조건).

**로컬 원문 자료 `docs/sources/`** (결정: 사용자가 구글 드라이브 자료를 이 폴더에 넣음 / 2026-11-03 확인)

- PDF 19개 + XLSX 1개. 모든 PDF는 국가법령정보센터에서 내려받은 것으로 **텍스트 레이어가 있다**(스캔본 아님, OCR 불필요).
- 이번에 쓰는 것:
  - `개인정보의 안전성 확보조치 기준(…)(제2026-9호)(20260701).pdf` — 28쪽. **고시 기준 버전 = 고시 제2026-9호, 2026. 7. 1. 시행.** 화면에 이 번호와 시행일을 표시한다.
  - `개인정보 보호법(3단비교).pdf` — 법률 제21445호 ↔ 시행령 제36671호 조문 대응. 세 번째 칸은 "연관된 시행규칙이 없습니다"로 비어 있다 → **3단비교에는 고시가 들어 있지 않음이 확인됐다.** 법 ↔ 영 연결의 원천 또는 API 결과 검증용으로 쓴다. 영 ↔ 고시 연결은 허브 매핑 seed로 만든다.
  - `법령체계도_개인정보_보호법.xlsx` — 법·시행령·행정규칙(고시) 19종의 이름·고시번호·시행일 목록. 「법령 문서」 참조 테이블의 seed로 쓴다.
- 나머지 고시 PDF(가명정보 결합, 영향평가, ISMS-P 인증 등)는 이번에 화면에 쓰지 않는다 (2.2 비목표). 폴더에 그대로 두고 나중에 같은 방식으로 추가한다.
- PDF 텍스트 추출은 **일회성 가져오기 스크립트**로 한다 (설계자 판단). 추출 → 조·항·호·목 구조로 나눔 → DB 저장. 추출 라이브러리는 devDependency로만 두어 런타임 의존성(NFR-6)은 늘리지 않는다. 추출 결과는 사람이 한 번 대조해 확인한다(특히 표·별표).
- 원문 출처 우선순위: **법률·시행령 = OPEN API 우선, 3단비교 PDF는 검증용 / 고시 = OPEN API(행정규칙) 우선, 실패 시 PDF.** 두 출처가 다르면 시행일이 더 최신인 쪽을 쓰고 경고를 출력한다.

**법령 버전** (설계자 판단)

- 조문은 **법령 문서의 버전**(공포번호·시행일)에 묶어 저장한다. 조 번호만으로 키를 잡지 않는다.
- 저장 대상: 현행 법률(제21445호), 시행 예정 법률(제21910호, 2027. 3. 9. 시행), 현행 시행령(제36671호), 현행 「안전성 확보조치 기준」.
- 3단 화면은 기본으로 현행 버전을 보여준다. 제28조의12~15처럼 시행 예정 법률에만 있는 조문은 시행 예정 버전 원문을 `🔜 2027. 3. 9. 시행` 표시와 함께 보여준다.
- 동기화 때 API가 주는 현행 공포번호가 위 기준과 다르면 **저장은 하되 경고를 출력**한다. 허브 매핑(단원 ↔ 조문)은 자동으로 바꾸지 않고, 사람이 확인한다.
- 허브 HTML 매핑과 API 원문의 조 번호·호 번호가 서로 다르면 **API 원문이 우선**한다. 매핑 seed는 고쳐서 맞춘다.

### 5.4 문의 게시판 (7단계)

- **작성 권한**: 로그인 사용자 누구나 질문·답변 **(결정)**.
- **목록**: 최신 글이 위. 답변이 1개 이상이면 **"답변 있음" 표시** **(결정)**, 답변 수도 함께 표시 **(설계자 판단)**. 조문 태그로 걸러 보기 가능 **(설계자 판단)**.
- **상세**: 질문 본문 아래에 답변이 작성 순으로 나열 **(결정)**. 답변 작성 폼은 맨 아래.
- **조문 태그** **(설계자 판단)**: 3단 화면에서 "질문하기"로 들어오면 조문(예: 법 제29조)이 자동으로 붙는다. 목록·상세에서 태그를 누르면 3단 원문 화면으로 이동. 게시판에서 직접 쓸 때 태그는 선택 사항.
- **수정·삭제** **(설계자 판단)**: 자기 글만. 답변이 달린 질문을 삭제하면 내용 대신 "삭제된 질문입니다"를 남기고 답변은 유지(소프트 삭제). 답변이 없으면 그냥 삭제해도 됨.
- 입력 검증: 제목·본문 길이 제한, 빈 글 금지. 본문은 일반 텍스트(줄바꿈만 유지), HTML 렌더링 안 함 **(설계자 판단)**.
- 페이지 나누기: 목록은 페이지당 고정 개수 **(설계자 판단)**.

## 6. 데이터 (개념 수준)

세부 컬럼·인덱스·제약은 `docs/DB_DESIGN.md`(1단계 산출물)에서 확정한다. 개념적으로 필요한 것:

- **사용자·세션**: users(`provider`, `provider_user_id` 유일), sessions(토큰 해시, 만료 시각).
- **학습 구조 참조**: 대단원(배점·색), 중단원, 세부 항목, 암기 카드, 기억 묶음(MNEMO), 개정 연혁, 장(법·시행령 각각).
- **조문**: 법령 문서(법률/시행령/고시, 공포번호, 시행일, 받은 시각), 조문(문서·조 번호(예: `24의2`)·제목·원문·시행예정 여부), 조문 간 연결(법 → 시행령 → 고시).
- **사용자 진도**: 중단원 회독 수, 카드 단계, 시험일.
- **게시판**: 질문(작성자·제목·본문·조문 태그·삭제 여부·시각), 답변(질문·작성자·본문·시각).

조 번호 표기는 허브와 같이 `24의2` 형식을 키로 쓰고 화면에서 "제24조의2"로 바꿔 표시한다.

## 7. 단계 계획 (CLAUDE.md 7장의 5~7단계 채움)

| 단계 | 작업 | 산출물 (예) | 완료 기준 |
|---|---|---|---|
| **5단계** | 구글 로그인 | 사용자·세션 테이블, 로그인/로그아웃 Server Action, OAuth 콜백 Route Handler, 세션 조회 서버 유틸 | 구글로 로그인 → 새로고침·`npm run dev` 재시작 후에도 로그인 유지, 로그아웃 동작 |
| **6단계** | 법령 대시보드 + 3단 원문 | 참조 데이터 seed SQL, 법령 API 동기화 스크립트, 대시보드 5개 탭, 3단 원문 화면, 진도 저장 Server Action | 법 제29조 → 영 제30조 → 고시 원문이 세 칸으로 표시, 회독 체크가 재시작 후 유지 |
| **7단계** | 문의 게시판 | 질문·답변 테이블, 목록/상세/작성/수정/삭제 화면, 조문 태그 | 3단 화면에서 질문 작성 → 다른 계정으로 답변 → 목록에 "답변 있음" 표시 |

**범위와 순서** (설계자 판단)

- 구현 계획은 **1~4단계부터** 포함한다. 저장소에는 아직 `PRD.md`, `docs/DB_DESIGN.md`, `docker-compose.yml`, Next.js 앱이 없다.
- 1단계 `docs/DB_DESIGN.md`는 계획 작성자가 이 문서 6장을 바탕으로 쓰되, **사용자 검토를 받은 뒤** 2단계(`init.sql`)로 넘어간다. 이것이 계획의 첫 체크포인트다.
- 6단계를 시작할 때 법령 API 승인(`LAW_API_OC`)이 아직 안 나왔으면 **7단계(게시판)를 먼저** 진행한다. 손으로 입력한 임시 원문은 쓰지 않는다 (2.3 실패 조건: 틀린 원문 방지). 게시판의 조문 태그는 조문 목록 seed(허브 `CHAPTERS`·`DECREE`)만 있으면 동작한다.

2단계의 `db/init.sql`에는 5~7단계에서 쓸 테이블을 모두 포함하거나, 단계별로 추가하되 최종적으로 하나의 스크립트로 재생성 가능해야 한다 (빌더 재량).

### 사용자가 직접 해야 하는 일

- Google Cloud Console에서 OAuth 클라이언트 생성, 승인된 리디렉션 URI에 `http://localhost:3000/auth/google/callback` 등록 → `.env`에 값 입력. (5단계 전)
- 국가법령정보센터 회원가입·OPEN API 활용신청 → 승인 후 `OC` 값을 `.env`에 입력. 승인에 1~2일 걸리므로 **지금 미리 신청**. (6단계 전)
